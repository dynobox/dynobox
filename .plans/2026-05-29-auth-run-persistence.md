## Overview (DYNO-5)
Dynobox currently runs locally as a stateless CLI. To turn it into a product, authenticated users need persisted run history that enables retention, pass-rate-over-time, and shareable run views. Runs must continue to work without authentication, and upload failures must never affect run exit codes.

This design adds a Cloudflare-backed product backend and Vite React dashboard app while keeping Supabase replaceable as an auth provider. Run metadata and compact display data are stored in Cloudflare D1 for the MVP. R2 is deferred until replay/full payload storage is built.

## Goals & Non-Goals
- **Goals**: Persist authenticated CLI runs without changing local run behavior.
- **Goals**: Support unauthenticated local-only runs.
- **Goals**: Add paste-based `dynobox login` with config file permissions `0o600`.
- **Goals**: Store API tokens hashed at rest in Cloudflare D1.
- **Goals**: Store compact run display data in D1 for dashboards and run pages.
- **Goals**: Build a minimal dashboard app at `dash.dynobox.xyz` with login, CLI auth, dashboard, and run detail pages.
- **Goals**: Keep backend API deployable separately from the Astro app.

## Technical Approach
- Add `apps/dash` as the Vite React UI for `dash.dynobox.xyz`.
- Add `apps/api` as a separate Cloudflare Worker backend for `api.dynobox.xyz` in the same pnpm workspace.
- Keep `dynobox.xyz` as the landing page and `docs.dynobox.xyz` as the documentation site.
- Use Supabase Auth only for browser login in `apps/dash`; do not store run data in Supabase.
- Follow-up: `DYNO-14` should move browser/session API authentication from app-forwarded identity headers to direct Supabase JWT verification in `apps/api`.
- Use Cloudflare D1 as the system of record for API tokens, run metadata, jobs, and assertions.
- Use opaque CLI API tokens generated by the backend and stored hashed in D1.
- Represent identity internally as `provider + subject_id` so Supabase can be swapped later.
- Add `packages/run-schema` for shared CLI upload payload validation and API typing.
- Keep the CLI run flow local-first: execute, render, compute failure exit code, then optionally upload.
- Use stderr for upload tips/status so `--reporter json` stdout remains valid NDJSON.
- Defer R2 until replay requires storing raw transcripts, tool events, chat history, or artifacts.

Database schema is managed with Wrangler D1 migrations, starting with `apps/api/migrations/0001_initial.sql`:
- `api_tokens`: `id`, `subject_id`, `provider`, `token_hash`, `created_at`, `last_used_at`, `revoked_at`.
- `runs`: `id`, `subject_id`, `provider`, `created_at`, `cli_version`, `schema_version`, `git_hash`, `target`, `status`, `pass_count`, `fail_count`, `warning_count`, `duration_ms`, `public`, `expires_at`, `summary_json`.
- `run_jobs`: `id`, `run_id`, `scenario_id`, `scenario_name`, `harness`, `model`, `iteration`, `status`, `passed`, `duration_ms`, `assertion_count`, `passed_assertion_count`, `failed_assertion_count`, `warning_count`, `details_json`.
- `run_assertions`: `id`, `run_id`, `job_id`, `assertion_id`, `label`, `kind`, `passed`, `message`.

API contracts:
- `POST /runs`: bearer token auth, validates `RunUploadV1`, inserts run, job, and assertion rows, returns `{ id, url }`.
- `GET /runs`: browser/session auth, returns recent runs and dashboard summary.
- `GET /runs/:id`: returns public run or owner-only private run.
- `PATCH /runs/:id`: owner-only updates such as `public`.
- `POST /cli-tokens`: browser/session auth, mints a one-time visible opaque token.

UI:
- `/login`: Supabase web login.
- `/cli-auth`: authenticated page that mints and displays a CLI token for paste login.
- `/`: authenticated pass-rate-over-time dashboard and recent runs.
- `/runs/:id`: basic run summary, matrix, failed jobs, assertions, and sharing state.

Testing:
- CLI unit tests for token resolution, login file permissions, upload success/failure, and unchanged exit codes.
- API tests for token hashing, invalid token rejection, run insert, ownership checks, and public reads.
- Schema tests for `RunUploadV1`.
- App smoke tests for dashboard/run route data loading.

## Risks & Mitigations
- Supabase coupling could leak into data models. Mitigation: store `provider` and `subject_id`, never semantic `user_id`.
- D1 row size may become limiting if payloads grow. Mitigation: store compact display data now and defer replay-grade payloads to R2.
- CLI upload could break JSON reporter output. Mitigation: write upload status only to stderr and add tests.
- Token leakage risk exists because CLI tokens are long-lived. Mitigation: hash at rest, use `0o600` local config, support revocation, and never log raw tokens.
- Run payloads may contain sensitive data. Mitigation: upload compact summaries only and exclude transcripts, workdirs, raw tool inputs, artifacts, and environment.
- Separate app/API deployments add routing complexity. Mitigation: keep both in the monorepo and use a stable public route contract on `api.dynobox.xyz`.

## Success Metrics
- Authenticated CLI runs appear in run history without changing local run behavior.
- Unauthenticated runs continue to pass existing CLI tests and skip upload.
- Upload failures produce warnings but preserve assertion-driven exit codes.
- Dashboard shows pass-rate-over-time grouped by `git_hash`.
- Single run pages show enough information to understand failures without replay.
- API tokens are stored only as hashes and config files are written with `0o600`.
- Supabase can be replaced by changing identity/session code without migrating run data.
